## Webサイト上での暗号化・復号

- 自分が持っているNFCタグに鍵データを書き込んでおくことで、その鍵を持っている人だけが閲覧可能なWebコンテンツ

これを作ることにしました。

指輪型NFCの仕様は、NTAG213で144bytesのデータ書き込みが可能です。
暗号化・復号の鍵データ単体であれば十分な容量です。

また、WebページでNFCタグを読み取るためのWeb NFC APIは現状、実質的にAndroid版Chrome（Chromium系ブラウザ）のみのサポートとなっていますが、幸い手元に対応端末があります。

## 技術解説

作成したものの中に、2つの重要なJavaScriptファイルがあります。

1. NFC読み取り関連ライブラリ: [webnfc-vault/js/nfc-key-reader.js at main · Nagatani/webnfc-vault](https://github.com/Nagatani/webnfc-vault/blob/main/js/nfc-key-reader.js)
1. 暗号化・復号ライブラリ: [webnfc-vault/js/crypto-vault.js at main · Nagatani/webnfc-vault](https://github.com/Nagatani/webnfc-vault/blob/main/js/crypto-vault.js)

それぞれ、Web NFC APIとWeb Crypto APIを用いています。参考文献としてMDNのリンクを貼っておきます。

1. [ウェブ NFC API - Web API | MDN](https://developer.mozilla.org/ja/docs/Web/API/Web_NFC_API)
2. [ウェブ暗号化 API - Web API | MDN](https://developer.mozilla.org/ja/docs/Web/API/Web_Crypto_API)

Web Crypto APIでは、暗号化方式はPBKDF2とAES-256-GCMを組み合わせて構築しています。

### 処理フロー

#### 事前準備: 暗号化フェーズ

ページ制作者が「NFCで開ける秘密のメッセージ」をWebサイトの公開用ファイル（HTML/JavaScript/JSON）へ組み込むために事前準備を行います。

1. パスワードの決定と指輪への記録
    * ランダムな鍵文字列（例: 32文字の英数字）を生成し、NFC指輪のメモリ内に書き込みます。
    * これが復号に必要な鍵データとなり、NFCタグに書き込むことで物理的な鍵と同等に扱います。
2. ランダム値（SaltとIV）の生成
    * ブラウザの暗号機能を用いて、使い捨てのランダムな値「Salt（ソルト/16bytes）」と「IV（初期化ベクトル/12bytes）」を生成します。
3. AES鍵の導出（PBKDF2）
    * 「指輪の鍵文字列」と「Salt」を混ぜ合わせ、10万回のハッシュ反復計算（ストレッチング）を行って、256ビットの厳密な暗号鍵（AES Key）を作り出します。
4. 暗号文と認証タグの生成（AES-256-GCM）
    * 生成したAES鍵とIVを使って、隠したい平文を暗号化します。
    * このとき、改ざん検証用の「認証タグ（MAC）」も自動生成されます。
5. 公開用データの作成
    * 「Salt」「IV」「暗号文（認証タグ含む）」をBase64文字列に変換します。
    * JSONデータでまとめられるので、HTMLに組み込んだり、Webサーバー等で公開します。
        - ※指輪の鍵文字列だけは絶対にHTMLへ含めません。


#### 閲覧: 復号・アクセス制御フェーズ

ユーザーがスマホでページにアクセスし、NFCタグを読込ませて隠されていたコンテンツを閲覧します。

1. Webページの読み込み
    * ユーザーがスマホのブラウザでWebページを開きます。
    * この時点ではHTML内に「暗号化された無意味な文字列」しか存在しません。
2. NFCスキャン待機と指輪の検知
    * ユーザーアクションにより、Web NFC APIが起動して待機状態になります。
    * NFCタグに書き込まれた「鍵データ（32bytes）」を読み取ります。
3. AES鍵の再生成
    * 読み取った「鍵データ（32bytes）」と、JSON内に埋め込まれている「Salt」を使い、暗号化時と同じ計算（PBKDF2 / 10万回計算）を実行して、ブラウザの内部メモリ上にAES鍵を復元します。
4. 復号と改ざん検証（AES-256-GCM）
    * 復元したAES鍵、JSON内の「IV」と「暗号文」を渡し、ブラウザ標準の復号処理を実行します。
        - 正規のNFCタグの場合: 認証タグの検証に成功し、平文（元のメッセージ）がメモリ上に復元され、画面に復号されたコンテンツが展開されます。
        - 鍵が違う場合: 認証タグの検証に失敗するため、Web Crypto APIが自動的に処理を破棄してエラーを発生させます。解読データは一切メモリ上に残らず、画面もロックされたままとなります。

## 要素技術の簡単な解説

1. 鍵導出関数: PBKDF2（Password-Based Key Derivation Function 2）
    * 人間やNFCが扱う「パスワード」を、暗号処理に適した「256ビットの厳密な暗号鍵」に変換します。
    * AES暗号は厳密に「256ビット（32bytes）のランダムなバイナリデータ」を鍵として要求します。
1. Salt: 暗号化ごとに `crypto.getRandomValues()` で16bytesの完全なランダム値を生成して混ぜます。
    * これにより、同じパスワードから生成されるAES鍵が毎回まったく違う別の値になり、あらかじめ計算されたハッシュ表（レインボーテーブル攻撃）を無力化します。
1. ストレッチング（100,000回の反復計算）
    * 意図的に計算負荷をかける仕組みです（コード中では `iterations: 100000`）。
    * スマホのブラウザでは即座に終わる軽い処理です。
    * 攻撃者がパスワードを総当たり（ブルートフォース）しようとすると、1秒間に数万回試行できなくなり、解読にかかる現実的な時間が数百年単位に跳ね上がります。
1. 暗号化アルゴリズム（AES-256-GCM）
    * AES: アメリカ国立標準技術研究所が制定した共通鍵暗号方式。広く推奨される暗号方式。
    * GCM（Galois/Counter Mode）: 暗号利用モードの1つ。こちらも広く推奨されている。
        - GCMは機密性と完全性を同時に保証する「AEAD（Authenticated Encryption with Associated Data）」です。暗号化と同時に認証タグ（Auth Tag / MAC）というハッシュ値を自動生成し、暗号文の末尾に付与します。
1. IV（初期化ベクトル / Nonce）
    * 12bytesの使い捨てするランダムな数値です。
        - ※AES-GCMでは同一鍵でのIVの再利用が致命的な脆弱性となるため、暗号化ごとに必ず新しいIVを生成します。
    * まったく同じ平文・同じパスワードであっても、暗号化するたびに生成される暗号文が毎回バラバラになるため、「暗号文のパターンから中身を推測する」攻撃を防ぐことができます。
        - ※IVは秘密にする必要はなく、復号時に必要なため、公開データと一緒に保存して問題ありません。
        


## 確実に間違った鍵を弾く

コード内の復号処理（`crypto.subtle.decrypt`）では、開発者が独自にパスワードの一致チェックコードを書いているわけではありません。

以下の処理では、間違った鍵、または暗号文が1文字でも改ざんされている場合、Web Crypto APIが自動的に例外を発生させます。

```javascript
await crypto.subtle.decrypt({ name: "AES-GCM", iv }, key, encryptedBytes);
```

間違った鍵でAES鍵を復元した場合、その鍵で暗号文を解こうとしてもGCMの認証タグの計算結果が一致しません。<br>
Web Crypto APIが「データの改ざん、または鍵の不一致」を検知し、復号処理自体を即座に破棄してエラー例外を投げます。<br>
そのため、中途半端に壊れた平文が漏れ出ることもなく、確実に不正なアクセスをブロックできます。


## 公開情報と非公開情報の境界

公開して良いもの: 

1. Salt
    - 事前計算された対応表（レインボーテーブル）による一括解読を防ぐための値。Salt自体が第三者に知られても鍵を逆算することはできないため
2. IV（初期化ベクトル）
    - 暗号文のユニーク性を担保する一時的な値。単体では無害のため
3. 暗号文
    - AES-256で暗号化されており、鍵がなければ解読困難（ほぼ不可能）なため
4. 認証タグ
    - そもそも暗号文に内包されているため

絶対非公開なもの:

1. NFCタグに書き込まれた鍵文字列
    - これが知られると暗号文は復号される
    - HTMLやJSファイル、ネットワーク送信のどこにも含めてはいけません

## クライアントサイドに暗号化・復号ロジックを含めて良いのか

結論から言えば、今回の用途であれば問題ありません。

よく「フロントエンド（JavaScript）に暗号化・復号ロジックを持たせるのはアンチパターン」と言われます。
これは主に「秘密鍵をコードにハードコードしてしまう」「平文通信の代替としてクライアント暗号化を行い、結局中間者攻撃や改ざんに対して無力になる」といった設計不備が原因です。

一方、今回の構成はエンドツーエンド暗号化（E2EE）と同様のモデルです。暗号文やロジックが公開されていても、復号に必要な鍵データは外部（物理NFCタグ）にしか存在せず、ブラウザのメモリ上でのみ一時的に処理されます。
数学的・計算量的に安全なアルゴリズムを用いている限り、クライアントサイドで復号を行うこと自体が脆弱性に直結することはありません。
